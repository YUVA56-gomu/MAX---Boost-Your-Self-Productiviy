# Agent Governance & Engineering Rules

## 1. Project Identity & Purpose
This repository hosts a **local-first adaptive productivity desktop application**. The application is designed to provide sovereign, privacy-first personal productivity management across **Four Core Pillars**:
1. **Task Management**: tasks, subtasks, priorities, deadlines, estimates, recurring tasks, and task history.
2. **Goals and Projects**: long-term goals, short-term goals, milestones, projects, and task-to-goal relationships.
3. **Habits and Focus**: habit tracking, focus sessions, Pomodoro timer, and scheduling.
4. **Insights and Reflection**: daily reviews, historical analytics, blockers, planned-versus-completed workload, and progress trends.
*Supporting Feature*: Contextual Notes & Knowledge Capture (embedded within projects, goals, and tasks).

The application operates **100% offline** and requires **zero cloud accounts, zero remote subscriptions, and zero remote network requests** for all core functionality. An optional local AI enhancement layer leverages **Ollama with Gemma 2 2B** running strictly on the user's local hardware.

- **Milestone 2: Core Data Engine & Backend Services (Four Pillars)** (`NOT_STARTED`)
  - Scope: Database models for all four core pillars + supporting notes, Alembic migrations, CRUD business logic, security middleware, and Pytest coverage.

  - Scope: Rust toolchain setup, Tauri 2 configuration, sidecar lifecycle management, native window controls.

## 3. Core Architectural & Security Rules

1. **Local-First & Offline Guarantee**:
   - All data is persisted in a local SQLite database (`journal_mode=WAL`).
   - Every core feature must be fully operational without an internet connection.
   - Network connectivity is never an application boot blocker.
2. **Sidecar Process Separation**:
   - Tauri 2 manages the native desktop shell and process lifecycle.
   - Python FastAPI runs as a local sidecar service bound exclusively to `127.0.0.1`.
   - Communication occurs via authenticated localhost HTTP REST / WebSockets.
3. **Security & Ephemeral In-Memory Token**:
   - 32-byte cryptographic token generated by Tauri shell at boot.
   - Passed via environment variable to sidecar and held in frontend memory.
   - **Never stored in persistent browser storage** (`localStorage`, `sessionStorage`, cookies, `IndexedDB`).
   - Constant-time per-request comparison (`secrets.compare_digest`).
   - All sensitive authorization headers and secrets are redacted from logs.
4. **Zero Telemetry & AI Sovereignty**:
   - Zero telemetry, phone-home metrics, or remote analytics.
   - Optional AI features use local Ollama with Gemma 2 2B.
   - No data mutations may be performed by AI without explicit human approval.
5. **Explicit Decision Rule**:
   - Every technical and product decision must be documented.
   - Never assume or invent undocumented requirements.
   - Any unresolved choice must be recorded as **`OPEN`** in `DECISIONS.md`.

## 4. Engineering Standards & Quality Gates

### 4.1 Frontend Standards
- **Framework**: React 18+ with TypeScript in strict mode (`"strict": true`).
- **Styling**: Tailwind CSS with shadcn/ui components; Gemini-inspired dark aesthetic tokens.
- **UI Specification & Reference Governance**: Before implementing or modifying any UI screen or component, agents **must read [`UI.md`](file:///d:/SelfProductivityApp/UI.md) and inspect the actual visual reference images** in `docs/design-reference/` (specifically `dashboard-reference.png`). Screens must adhere strictly to the layout, tokens, component anatomy, and state specifications defined in `UI.md` and `DESIGN_SYSTEM.md`.
- **State Management**: TanStack Query for server-state caching; Zustand for ephemeral UI state.
- **Testing**: Vitest + React Testing Library for component and unit testing.

### 4.2 Backend Standards
- **Runtime**: Python 3.14.0 (empirically verified with `uv`).
- **Framework**: FastAPI with Pydantic v2 schemas for all request/response models.
- **ORM & Migrations**: SQLAlchemy 2.0 (mapped declarative models) + Alembic.
- **Testing**: Pytest with in-memory SQLite fixtures and dedicated security test cases.

### 4.3 Shell & Environment Standards
- **Host OS**: Windows (PowerShell environment).
- **Path Handling**: Use forward slashes (`/`) in markdown links and URI formats. Avoid unescaped Windows backslashes in script strings.
- **Never claim untested commands**: Never state that a build, test, or executable succeeded unless it was executed and verified during the session.

## 5. Mandatory Tracking & Updates After Every Task

After completing each meaningful task, agents must perform the following documentation updates before ending the turn:
1. **Update `IMPLEMENTATION_PLAN.md`**: Update task and subtask status checkboxes and record completion evidence.
2. **Update `PROJECT_STATUS.md`**: Update current task, overall milestone status, verified criteria, and timestamp.
3. **Append to `TASK_LOG.md`**: Record the chronological work log entry (timestamp, files changed, commands/tests executed, actual results, errors/resolutions, and remaining work).
4. **Update `DECISIONS.md`**: If an architectural or design decision was made, refined, or marked open.
5. **Update Contracts / Specifications**: If implementation refined an API endpoint, data schema, or UI specification.
6. **Execute Verification**: Run the applicable test/build command and record actual verbatim results.

## 6. Session Recovery Protocol

At the start of every new session or after context loss, agents must execute the following sequence before proposing or executing work:
1. Read **[`AGENTS.md`](file:///d:/SelfProductivityApp/AGENTS.md)** to reload operating governance and constraints.
2. Read **[`PROJECT_STATUS.md`](file:///d:/SelfProductivityApp/PROJECT_STATUS.md)** to determine active milestone, phase, blockers, and next action.
3. Read the active milestone section in **[`IMPLEMENTATION_PLAN.md`](file:///d:/SelfProductivityApp/IMPLEMENTATION_PLAN.md)**.
4. Review the latest entries in **[`TASK_LOG.md`](file:///d:/SelfProductivityApp/TASK_LOG.md)** to inspect recent accomplishments, test outputs, and unresolved issues.
5. Check actual repository state and files on disk.
6. Compare documented progress with physical files and test evidence. Never assume work is complete without verification.
7. Resume strictly from the last verified incomplete task.

## 7. Milestone Gatekeeping Protocol

Milestone transitions follow strict gatekeeper validation:
1. **Explicit Statuses**: Every milestone and task must use one of:
   - `NOT_STARTED`
   - `IN_PROGRESS`
   - `BLOCKED`
   - `IN_REVIEW`
   - `COMPLETED`
2. **Completion Criteria**: A milestone may transition to `IN_REVIEW` only when:
   - All assigned tasks and subtasks are completed.
   - All defined acceptance criteria are verified with passing tests or audit checks.
   - Documentation is 100% consistent with implementation.
   - Known limitations and blockers are logged.
3. **Human Gatekeeper Sign-Off**:
   - A milestone in `IN_REVIEW` cannot be marked `COMPLETED` until the user explicitly reviews and approves the report.
   - Agents **must never start the next milestone automatically**.

## 8. Standard Final Handoff Format

Every agent response concluding a task or session must present:
1. **Current Milestone & Status**: (e.g. `Milestone 0: IN_REVIEW`)
2. **Tasks Completed in this Session**: Bulleted summary of accomplishments.
3. **Files Changed**: Clickable links to created or modified files.
4. **Commands & Tests Actually Executed**: Verbatim commands and exit codes.
5. **Failures, Blockers & Open Decisions**: Explicit list (or "None").
6. **Exact Next Recommended Action**: Clear statement of the immediate next step.
7. **User Approval Gate**: Clear notice whether user approval is required to proceed.
